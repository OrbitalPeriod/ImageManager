## Project Overview

ImageManager is a full-stack anime image management platform with three main components:
- **Backend (ImageManager)**: ASP.NET Core 9.0 REST API with Entity Framework, PostgreSQL, and gRPC client
- **Frontend**: Next.js 16 (React 19) with TypeScript, TailwindCSS, and openapi-fetch
- **AnimeTagger**: Python gRPC service using wdtagger for ML-based anime image tagging

The system allows users to upload, tag, search, and manage anime images with automatic AI tagging, character detection, and age rating classification.

## Architecture

### Backend Architecture

**Layered Architecture Pattern:**
- **Controllers** (`ImageManager/Controllers/`): API endpoints following REST conventions
- **Services** (`ImageManager/Services/`): Business logic organized by domain (Admin, Character, File, ImageImport, Tags, etc.)
- **Repositories** (`ImageManager/Repositories/`): Data access layer with interfaces and implementations
- **Workers** (`ImageManager/Workers/`): Background services (hosted services) for async processing
- **Data Models** (`ImageManager/Data/Models/`): Entity Framework entities

**Key Patterns:**
- Repository pattern with interfaces in `Repository Interfaces/` and implementations in `Implementations/`
- Channel-based async processing for image imports and platform syncs (see Program.cs channels)
- Cookie-based authentication with ASP.NET Identity
- gRPC client for AnimeTagger service (proto at `Protos/AnimeTagger.proto`)

**Background Workers:**
- `RemoteSyncService`: Syncs images from external platforms (Pixiv)
- `RemoteSyncQueuingService`: Queues platform sync requests
- `FolderImageImportService`: Imports images from filesystem folders
- `QueuedImageImportService`: Processes queued image imports after AnimeTagger becomes available

**Database:**
- PostgreSQL with EF Core
- Schema: `identity` (default)
- Key entities: `Image`, `UserOwnedImage`, `Character`, `Tag`, `DownloadedImage`, `ShareToken`, `PlatformToken`
- Images are deduplicated by perceptual hash (`Image.Hash`)
- Many-to-many: Images ↔ Tags, Images ↔ Characters
- Users can own images with different publicity levels (Private, Unlisted, Public)

### Frontend Architecture

**Next.js App Router:**
- Server components by default
- Client components in `frontend/src/components/`
- API routes handled by backend (not Next.js API routes)

**API Client Pattern:**
- Type-safe API client generated from OpenAPI spec (`src/lib/api/client.ts`)
- `createApiClient()` for generic usage
- `getClient()` for client-side (browser fetch + cookies)
- `getServerClient(cookies)` for server-side (forwards cookies from request)
- All API calls use cookie-based authentication

**Key Directories:**
- `src/app/`: Next.js pages (admin, image, login, register, platform-tokens)
- `src/components/`: Reusable React components
- `src/lib/api/`: API client configuration
- `src/lib/auth/`: Authentication hooks and middleware
- `src/lib/hooks/`: Custom React hooks (use-api, use-pagination)
- `src/lib/errors/`: Error types and handlers

### AnimeTagger Service

- gRPC service on port 50051
- Single RPC: `GetTags(ImageMessage) → ImageResponse`
- Uses wdtagger library for anime image classification
- Returns character tags, general tags, and age rating (General/Sensitive/Questionable/Explicit)
- Health check available via grpc-health-probe

### Multi-User & Permissions

**User Roles:**
- Regular users (default): Can upload and manage their own images
- Administrators: Can approve users, promote/demote admins, manage all images

**Publicity Levels (Enum):**
- `Private` (0): Only owner can see
- `Unlisted` (1): Accessible with share token
- `Public` (2): Visible to all

**Share Tokens:**
- Time-limited tokens for sharing private/unlisted images
- Created per-image via `/api/ShareToken/add/{imageId}`

**Platform Tokens:**
- Connect external platforms (currently Pixiv)
- Sync liked/bookmarked images from platform
- Each token tracks sync logs

### Image Storage

Images are stored on filesystem:
- Original images: `/Images/{imageId}`
- Thumbnails: `/Images/{imageId}_thumb` (if `HasThumbnail` is true)
- Compressed: `/Images/{imageId}_compressed` (if `HasCompressedVersion` is true)

Mounted in Docker at `/Images` volume.

### Database Relationships

```
User
├── UserOwnedImages[] (images owned by user)
├── ShareTokens[] (share tokens created by user)
└── PlatformTokens[] (connected platforms)

Image
├── UserOwnedImages[] (users who own this image)
├── Tags[] (many-to-many)
├── Characters[] (many-to-many)
└── DownloadedImage? (source info if imported from platform)

UserOwnedImage
├── User
├── Image
└── ShareTokens[] (share tokens for this user's copy)
```

## Development Notes

### When working with the backend:
- All entities use `Guid` as primary key with `gen_random_uuid()` default
- Services use dependency injection - register in Program.cs
- Controllers inherit from `ControllerBase`
- Use `[Authorize]` attribute for authenticated endpoints, `[Authorize(Roles = "Administrator")]` for admin-only
- API responses should use `ProblemDetails` for errors
- Channel-based queuing for async work: write to channel, worker reads from channel

### When working with the frontend:
- Use server components where possible for better performance
- Client components need `'use client'` directive
- API calls on server: `getServerClient(cookies().toString())`
- API calls on client: `getClient()`
- Regenerate API types after backend OpenAPI spec changes: `npx openapi-typescript ./src/lib/api/spec.yaml -o ./src/lib/api/client.ts`

### When working with gRPC:
- Proto file at `ImageManager/Protos/AnimeTagger.proto`
- Backend uses Grpc.Net.Client to call AnimeTagger
- AnimeTagger uses grpcio (Python)
- If proto changes, regenerate both backend (automatic via Grpc.Tools) and Python code

### Database Migrations:
- Generate: `cd ImageManager && dotnet ef migrations add "Description"`
- Apply: `dotnet ef database update`
- Migrations are in `ImageManager/Migrations/`

### Environment Variables:
- Backend requires: `SQL_CONNECTION_STRING`, `CORS_ALLOWED_ORIGIN`
- Frontend requires: `NEXT_PUBLIC_API_URL`
- Store in `.env`, `.docker.env`, `.secrets.env` (see docker-compose.yml)

### Testing:
- Backend: No test framework configured yet
- Frontend: TypeScript checking via `npm run test:ts`
